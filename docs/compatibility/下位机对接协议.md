# 下位机对接说明：连接握手与急停复位

本文供下位机程序开发、调试人员使用，说明本次调整的两个流程：**连接握手**和**急停解除后的复位同步**。

上下位机必须使用相同的串口参数。本文报文示例采用默认 ICT ASCII 协议；已有厂家使用其他协议适配器时，保留双方已确认的表头和结果字段格式，遵守本文的发送顺序。

文中 `\r\n` 表示实际的回车、换行两个字符，不是发送反斜杠加字母的文本。命令大小写、结束符应按双方配置一致实现。

## 一、连接握手：下位机收到命令后应如何回复

### 1.1 连接成功的判断方式

上位机通讯设置提供两种互斥的连接握手方式，**只能勾选其中一种，也可以都不勾选**。勾选一项时，界面自动取消另一项：

- **IsOpen 握手**：界面名称为“用 IsOpen 回复判断连接成功”。
- **Itemnum 表头判断**：界面名称为“用 Itemnum 表头响应判断连接成功”。

| IsOpen 握手 | Itemnum 表头判断 | 上位机连接流程 | 下位机必须实现 |
| --- | --- | --- | --- |
| 不勾选 | 不勾选 | 串口成功打开，显示“已连接” | 无连接握手要求；仍需按业务流程处理表头、测试等命令。 |
| 勾选 | 不勾选 | 打开串口 → 发送 `IsOpen` → 收到 `1` → 显示“握手成功” | 收到 `IsOpen` 后回复独立的 `1`。 |
| 不勾选 | 勾选 | 打开串口 → 发送 `Itemnum\r\n` → 收到完整有效表头 → 显示“握手成功” | 收到请求后回复完整的 `Item1...;end`。 |

**不支持同时勾选 IsOpen 和 Itemnum 作为连接判据。** 下位机按现场选定的一种方式响应连接握手。

**两个选项都不勾选时，“已连接”只表示串口打开成功，不代表已验证下位机应答。**

### 1.2 IsOpen 握手报文

默认报文及方向：

```text
上位机 → 下位机：IsOpen
下位机 → 上位机：1
```

下位机实现要求：

1. 通讯接收程序能够正常响应时，收到 `IsOpen` 就回复 `1`。此命令只检查通讯，不启动测试、不执行复位、不驱动设备动作。
2. 回复内容为独立的 `1`，可带回车换行。不要回复 `IsOpen=1`、`OK`、调试文字或其他混合内容。
3. 默认请求为原文 `IsOpen`，**上位机不自动追加回车换行**。如果下位机按行接收，双方应将“握手发送命令”明确配置成 `IsOpen\r\n`。
4. 上位机在下位机通讯配置的“超时(ms)”内等待回复。超时或回复内容不符合期望时，本次连接失败，不继续发送连接后的表头请求。
5. 握手命令和期望回复可配置。本文以默认值 `IsOpen`、`1` 为准，现场修改后以实际配置为准。

### 1.3 Itemnum 请求与表头回复

默认报文及方向：

```text
上位机 → 下位机：Itemnum\r\n
下位机 → 上位机：Item1,Voltage,5,0,V;Item2,Current,2,0,A;2;end
```

以上示例表示两个测试项。默认 ICT 表头每一项的字段顺序为：

```text
Item项目序号,名称,上限,下限,单位[,点位A,点位B];
```

下位机实现要求：

1. 收到 `Itemnum` 后，回复当前实际使用的完整测试项列表。不要只回复数量、`1` 或 `OK`。
2. 表头从 `Item1,` 开始，项目序号从 1 连续递增，整条表头以 `;end` 结束。示例中末尾的 `2;` 是项目总数段；默认 ICT 适配器兼容带或不带该段的表头。
3. 每项至少包含序号、名称、上限、下限、单位五个字段。名称及字段内容不要包含未约定的英文逗号或分号，以免被当作分隔符。
4. 表头较长时可以分多次串口写入，但必须保持连续顺序。从 `Item1,` 到 `;end` 之间不得插入测试结果、握手回复或其他调试内容。
5. `Itemnum` 是读取测试项的请求，重复收到时不得启动测试。下位机应将请求串行处理；如果正在发送表头，应合并重复请求或排队处理，不能同时启动多个表头发送任务。

上位机未收到表头首段时，会按配置的重试间隔最多请求 3 次；收到 `Item1` 首段后停止重试，等待完整 `;end`。完整报文的接收超时使用“下位机报文接收超时”配置。**只有完整表头解析通过，Itemnum 连接判断才算成功。**

### 1.4 “连接后请求测试项”与连接判据的关系

上位机原有的“连接后请求测试项”选项，控制连接及复位后的主动表头请求。它可以与任意一种连接握手方式配合使用；此选项不属于互斥的两个握手勾选项：

| 配置情况 | 实际行为 |
| --- | --- |
| 启用 Itemnum 表头判断 | 连接时必定请求表头，即使“连接后请求测试项”没有勾选。 |
| 仅启用 IsOpen 判断，同时勾选“连接后请求测试项” | IsOpen 握手成功后，再请求表头；此时表头不作为本次连接成功的额外条件。 |
| 两个连接判据都关闭，同时勾选“连接后请求测试项” | 串口打开即判定已连接，随后仍请求表头。 |
| Itemnum 判断和“连接后请求测试项”都关闭 | 上位机不主动发送表头请求；若需同步表头，必须另行约定下位机主动发送。 |

选择 IsOpen 握手后，仍可能因为“连接后请求测试项”已启用而收到 Itemnum。此时 **IsOpen 用于判定连接，Itemnum 用于加载测试项**，并非同时启用了两种连接握手。下位机应先回复 IsOpen，再在收到 Itemnum 请求时返回表头。

**本说明第二部分采用“收到 reset 后由上位机请求表头”的方式，因此现场必须开启“连接后请求测试项”或 Itemnum 表头判断，至少一项。**

### 1.5 连接联调应验证

- 勾选 IsOpen 时，正确回复 `1` 可以连接；无回复或回复 `0` 应连接失败。
- 勾选 Itemnum 时，完整有效表头可以连接；无回复、缺少 `;end` 或表头格式错误不能通过。
- 先勾选 IsOpen，再勾选 Itemnum，IsOpen 应自动取消；反向切换也应自动取消另一项，不能同时选中。
- 选择 IsOpen 并启用“连接后请求测试项”时，回复 `1` 后仍需响应后续 Itemnum 请求；该请求用于加载表头。
- 两项都不勾选时，串口成功打开即可显示“已连接”。
- 握手过程不引起测试启动或设备动作。

## 二、急停复位：解除急停后如何结束旧周期、同步新表头

### 2.1 reset 的发送方和发送时机

当前约定：**操作员人工解除急停后，由下位机向上位机发送 `reset`。**

发送 `reset` 前，下位机必须完成以下动作：

1. 中止急停前正在进行的测试，使该测试不能继续生成旧周期结果。
2. 停止旧周期的结果发送任务，并清理尚未发送的旧结果队列。
3. 确保已交给串口驱动的残留旧数据排在 `reset` 前面，不会在 `reset` 后继续出现。
4. 通讯程序已能够接收并响应上位机随即发来的 `Itemnum` 请求。

**reset 的含义是“旧周期已停止、可以重新同步表头”。下位机不能只检测到急停解除就立即发 reset，然后继续发送旧结果。**

本文的 `reset` 是通讯通知。设备急停停机和恢复条件由设备原有控制流程执行，不能等待通讯回复后才停机。

### 2.2 双方必须遵守的完整顺序

| 顺序 | 操作方 | 动作 |
| --- | --- | --- |
| 1 | 操作员 / 下位机 | 按下急停；设备立即停机，中止当前测试，停止生成及发送旧周期结果。 |
| 2 | 操作员 | 人工解除急停。 |
| 3 | 下位机 | 确认旧结果发送任务已停止、待发送旧数据已清理，然后发送独立的 `reset`。 |
| 4 | 上位机 | 收到 `reset`，作废未完成的测试周期并清空未完成接收缓存，立即发起表头请求。**不等待上次测试结果补齐。** |
| 5 | 下位机 | 收到 `Itemnum` 后，完整、连续地发送当前 `Item1...;end` 表头。 |
| 6 | 上位机 | 收齐并校验表头，校验通过后等待下一轮测试。 |
| 7 | 下位机 / 操作员 | 按既有生产启动条件产生新的 `DM`，再按原有扫码、启动测试和结果发送流程执行新周期。 |

对应报文时序：

```text
操作员按下急停
    ↓
下位机停机、中止旧测试、停止旧结果发送
    ↓
操作员人工解除急停
    ↓
下位机确认旧发送任务和旧队列已清理
    ↓
下位机 → 上位机：reset\r\n
上位机 → 下位机：Itemnum\r\n
下位机 → 上位机：Item1,Voltage,5,0,V;Item2,Current,2,0,A;2;end
    ↓
表头同步完成，等待下一次生产启动
    ↓
下位机 → 上位机：DM
    ↓
按原流程扫码、启动新测试
    ↓
下位机 → 上位机：Test1,4.95,OK;Test2,1.20,OK;2;end
```

### 2.3 下位机必须处理好的报文边界

- **不要先补发上次结果再复位。** 急停中断的旧周期按作废处理，不要求补齐旧 `Test1...;end` 后才允许发送 `reset`。
- **reset 后禁止补发旧结果。** 包括后台任务、定时器、重发队列中残留的旧 `Test` 数据。
- **reset 单独发送。** 建议使用 `reset\r\n`；不要把它作为 Item 或 Test 的字段。即使旧报文已经发送了一部分，也应先终止旧发送任务，再通过同一发送队列发送 reset。
- **表头与结果不能交叉发送。** 同一通讯口只能有一个统一的发送队列；整条 `Item1...;end` 写完前不能穿插 `Test`。长报文分次写入时，也要保证整条报文的发送顺序。
- **复位后先完成表头同步，再进入下一次启动流程。** reset 和表头回复都不表示自动开始测试。

### 2.4 对接中容易误解的几个问题

| 问题 | 本次约定 |
| --- | --- |
| 是上位机发送 reset，还是下位机发送？ | 下位机发送，上位机接收。 |
| 急停按下就发 reset 吗？ | 当前约定是人工解除急停后发送；发送前还必须停止并清理旧周期数据。 |
| 上位机收到 reset 后什么时候请求表头？ | 在已启用主动表头请求的配置下立即请求，不等待旧结果，也不等待下一次 DM。 |
| 复位后会重新发送 IsOpen 吗？ | 串口仍保持连接时，不重复进行 IsOpen 连接握手；本次恢复通过重新请求表头同步。断线重连时才重新执行所选连接握手。 |
| 下位机回复表头后，还要等一个“表头确认”命令吗？ | 当前没有新增此类确认命令。上位机在本地校验表头，不向下位机发送额外的表头成功应答。联调时通过上位机日志确认解析成功。 |
| 只收到 Item1 首段就可以发送新结果吗？ | 不可以。必须先完整发送整条表头到 `;end`，再按新的 DM 及既有启动条件进入新周期。 |
| 收到重复 Itemnum 怎么办？ | 按同一个只读请求串行处理，不能启动多个并行发送任务，也不能触发测试。 |
| 无法保证 reset 后没有旧数据怎么办？ | 需要先修改下位机的测试任务和发送队列管理；不能靠固定延时保证顺序。 |

### 2.5 复位联调应验证

1. 在正在发送测试结果时按急停，人工解除后，日志中能看到 `reset → Itemnum → 完整 Item1...;end`。
2. reset 之后没有旧周期 `Test` 尾段、补发或重发；被急停中断的未完成周期不作为一次有效测试保存、计数或上传。
3. 分多次发送长表头，表头内部没有混入 Test、其他表头或调试信息。
4. 表头发完后不自动测试；下一次通过新的 DM 和既有业务启动条件进入新周期。
5. 连续执行多次急停、解除、复位，仍能保持上述顺序，且没有多个发送任务并行输出。
